## Summary
Wilson's mobile browser screenshots showed that short Chef It Up setup/selection screens, Ticket Pass, Prep Tray, Ready Check, and the Slop Bowl flow can overfill the visible Chrome/Safari viewport even though the accepted object proportions still feel right. The clarified rule is not to make every page tiny: short interactions should expose their useful controls in the same mobile-browser viewport before scrolling where practical, while long content pages only need to start cleanly at the top. The latest refinement from screenshots 12-32 approves moving from per-page pixel fitting to browser-mode principles: top content must start cleanly below browser chrome, primary next actions should float above the bottom app nav, secondary actions remain in page flow, floating back controls should not consume layout height, similar text levels should stay visually consistent, the bottom app nav can be shorter to make room, setup camera objects should not let off-state text overlap bottom controls, decorative setup viewfinder corners should be removed when they do not serve a user-facing purpose, and first-time setup scrollports should end at the Back/Next rail instead of exposing inert blank space below it. Screenshot 32 shows the normal planning choice page already has an acceptable endpoint; screenshots 29-31 show the remaining blank-tail bug belongs to the first-time setup/profiling shell and requires one clear mobile scroll owner. This branch now implements those principles for the MealPlanning short-flow screens, Slop Bowl pantry-check/approval/feedback, Ready Check's pre-start `Start cooking` action, and the first-time/returning setup camera object, keeps long Pantry/Settings examples as scrollable long content while normalizing their same-level browser-mode typography where it drifted, and preserves the explicit exclusions for Live Cooking preparing/active cockpit surfaces, Menu drawer typography, and the public/pre-login landing hero. Wilson's latest review says the Chef It Up/Slop It Up proportions now look good in the mobile browser, but the floating back button can still cover titles; treat that overlap as future redesign debt, not as solved by this branch.

## Impact on other agents
Treat `.meal-planning-screen` as the broad MealPlanning browser-fit hook, `.planning-browser-action-screen` as the opt-in wrapper for pages with a floating browser-mode primary action/back control, `.planning-action-dock` / `.planning-primary-action` as the primary action dock, `.planning-time-screen`, `.planning-cuisine-screen`, `.planning-tickets-screen`, and `.planning-prep-screen` as the short-interaction sizing hooks, `.setup-scan-step` as the first-time setup scanner hook, `.setup-ui` / `.setup-phone-frame` as the mobile setup scroll-ownership pair, `.setup-camera-state` / `.setup-camera-controls` as the NativeCamera state/control layout hooks, `.live-cooking-ready-check-screen` as the pre-start Ready Check exception, `.returning-profile-panel` as the Cooking Profile browser-type hook, and `.slop-bowl-approval-screen` / `.slop-approval-actions` / `.slop-bowl-feedback-screen` as Slop Bowl action-stack hooks. Do not move these overrides back onto shared `.planning-screen` or broad `.returning-panel`; that would risk pulling in surfaces Wilson explicitly said look okay. Do not add local `text-lg` or similar one-off utilities back onto `.planning-primary-action` buttons; same-level primary actions should share the same computed font size across Chef It Up, Slop It Up, and Ready Check. Chef It Up screens with fixed/floating back controls still need a future redesign pass because the button can cover centered titles; the current branch reduces but does not solve that. Keep `.menu-sheet`, the public/pre-login landing hero, the Live Cooking preparing/loading card, the active Live Cooking cockpit, and long Pantry/Settings inventory pages out of forced same-viewport fitting unless Wilson reopens those surfaces. Long returning Settings inventory pages may still receive short-browser typography normalization when their headings, action rows, chips, inputs, or save actions visibly drift from the Planning type levels; Settings hub/Profile/History may use the same short-browser typography scale because they are utilitarian returning-user surfaces, not landing heroes. Slop Bowl pantry-check is long content for its chip list, but it now participates in the floating primary-action/back-control browser pattern. The no-inert-bottom-tail rule is now in `design_guidelines.md`; it now explicitly includes single scroll-owner behavior for mobile browser setup shells. If the broader floating primary-action system passes phone-browser review, promote those remaining principles fully too.
